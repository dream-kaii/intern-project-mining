# 项目画像（Stage 0–1）

## Stage 0 信息收集清单

一次问 1–2 个问题，按需收集；问完 5 项即收口进入 Stage 1，不重复追问：

1. **项目代码位置**：本地路径（推荐）；无法提供代码时，让用户粘贴 README / 目录结构 / 技术栈摘要。
2. **岗位方向**：后端 / 前端 / 测试 / 运维 / 数据，或具体语言框架。
3. **实习时间**：剩余时长、每周可用时间。
4. **已完成工作**：改过哪些模块、做过哪些需求。
5. **简历时间线**：什么时候开始投递、主投哪些岗位类型。

代码无法回答的业务问题（如业务量级、部署环境、状态机细节）不在此阶段反复追问，放到 Stage 1 以「提问/待确认」处理。

## 开场保密提醒（固定附上）

- 本分析只在本机进行：不调用外部网络工具，不把代码粘到任何外部服务。
- 不要上传含密钥、内网地址、数据库口令、客户数据的文件；敏感项目先过滤再分析。
- 输出中不粘贴大段原始代码；为方便对照会保留类名、文件路径与行号引用，敏感业务数据转述。
- 说明：以上措施把泄露面降到最小，但无法保证绝对安全。

## 后端项目读码清单（按需执行，不必全做）

- README / 项目文档：业务定位、快速启动、架构说明
- 构建与依赖：pom.xml / build.gradle / go.mod / package.json、关键依赖与版本
- 目录结构：模块划分、分层（controller / service / dao / domain 等）
- 入口与启动：main 类、配置文件、环境与 profile
- 数据模型：实体、表结构、迁移脚本
- 接口：Controller/Router 清单、OpenAPI 文档、典型请求链路
- 基础设施：消息队列、缓存、定时任务、第三方依赖（支付/短信/推送等）
- 工程设施：测试、CI/CD、监控、日志、部署脚本

## 项目完整性检查（进入 Stage 1 时先做）

拿到项目后先判断项目是否完整可用，再决定后续怎么挖：

检查项：
- README / 文档是否存在且可理解
- 构建配置（pom.xml / build.gradle / go.mod / package.json）是否存在、依赖是否完整可解析
- 主入口 / 启动类是否存在
- 关键模块是否有真实实现（区分「空壳/占位」与完整代码）
- 数据模型 / 迁移脚本 / 配置（含环境变量占位）是否齐全
- 是否存在测试目录
- 明显缺失：TODO 空实现、缺失文件、编译报错、无版本控制

输出：
- 完整性结论：完整 / 基本完整 / 明显缺失
- 缺口清单：每条注明「影响哪些阶段」和「需要用户补什么」
- 若项目无法本地运行（缺 DB/外部服务），复现练习仍可做代码级复现，但要向用户说明限制

注意：完整性结论只基于能看到的事实；缺失不等于不存在（可能是没提供权限/目录），先问用户确认再下结论。

## 项目画像输出模板

### 一句话定位
产品做什么、给谁用、解决什么问题（代码里看不出时问用户）。

### 业务背景
- 目标用户与典型场景
- 核心业务流程（从触发到结束的完整链路）
- 业务价值点

### 技术栈
- 语言与框架、关键中间件、部署方式
- 标注哪些是当下主流/重要技术（缓存、MQ、分布式、高并发、数据库、性能等），供 Stage 2 优先选择

### 架构分层
- 模块划分、依赖关系、数据流向（附一张简洁的文字版架构图）

### 核心模块与数据流
- 每个核心模块：职责、对外接口、依赖、关键数据

### 已有工程设施
- 测试覆盖、CI/CD、监控告警、日志链路、代码规范

### 待确认项
列出所有不确定、需要用户补充/确认的信息（包括代码无法回答的业务问题）。

输出画像后，请用户确认或纠正，再进入 Stage 2。
