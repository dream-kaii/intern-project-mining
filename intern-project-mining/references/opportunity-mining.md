# 含金量机会挖掘（Stage 2）

目标：找出「实习生能承接、做完能写进简历、面试能延伸讲出八股文、符合实习期真实工作量」的**技术向开发需求**。每个机会必须能写代码或做代码级优化，且必须同时包含「需求背景」「对应解决方案」「技术栈/技术点」「面试延伸（八股文考点）」四项。

## 实习生适配校准（先校准，再挖掘）

- Stage 0 已收集实习时长（已结束的 = 实际实习月数）。按 `references/intern-requirement-patterns.md` 校准**建议产出条数**和**允许级别**：2 个月以内只做 L1（1 条核心）；3–4 个月 L1 为主（1–2 条）；6 个月及以上可带 L2（2–3 条）。
- 默认只挖 L1 实习生友好需求 + 少量 L2；L3（整体缓存架构、分布式事务、MQ 架构、核心支付/资金链路）不输出为机会，仅作理解。

## 硬性筛选（先过滤再挖掘）

不符合以下任一条件的机会直接排除：
- **不是开发需求**：不能写代码或做代码级优化（如搭接口文档、写流程规范、整理表格、纯配置搬运、会议排期）
- **没有可讲的技术点**：做完无法延伸出任何技术原理、取舍或坑
- **没有代码证据**：无法从项目代码中定位到改动点。接口文档体系这类「肯定存在但不在仓库里」的事直接排除——仓库里没有、也讲不出技术
- **超出实习期工作量/能力/权责**：按实习月数校准后无法完成、或明显超出实习生能力边界（如设计整套缓存架构、分布式事务、动核心支付/资金链路）→ 排除或降级。宁可小而扎实，不可大而空
- **适配性**：面试官深挖时讲不清实现细节、踩过的坑、量化数据来源 → 排除或拆小

## 机会输出模板

每个机会输出以下字段：

1. **机会名称**：一句话，如「订单查询接口加 Redis 缓存」
2. **级别**：L1 / L2（必须符合实习月数校准）
3. **需求背景**：为什么做、业务价值、现状痛点（代码里能看出的客观现状 + 用户补充）
4. **对应解决方案**：技术方案、涉及模块与改造点、风险、验收标准（可量化）
5. **技术栈/技术点**：落到具体技术（Redis、Kafka、MySQL 索引、Spring Task 等），并注明是否是当下主流/重要技术
6. **面试延伸（八股文考点）**：能延伸讲到的经典考点清单 + 一句「怎么从项目经历自然过渡到这个考点」
7. **含金量理由**：为什么值得写简历（可量化、可讲取舍、体现工程化能力）
8. **难度与预估工时**：低/中/高 × 1 天/1 周/1 月（与实习月数匹配）
9. **简历关键词映射**：如「Redis 缓存」「SQL 优化」「MQ」「定时任务」
10. **代码证据强弱**：强（代码里直接可见）/ 中（代码可推断）/ 弱（需线上情况佐证）/ 待确认；弱证据默认不直接写进简历
11. **关联机会**：与哪些机会同源/可能重叠，同源标注「二选一」
12. **简历写法参考（一句话）**：可直接用的简历描述，如「给 XX 查询接口增加 Redis 缓存并设计 key 与过期策略」
13. **量化数据与口径**：每个量化数字配套说明数据来源与测量方法（JMeter 压测 / 日志统计 / explain 前后对比 / Redis INFO / 监控大盘）、统计周期、对比基线；未实测标注「计划口径」

## L1 实习生友好需求模板（在项目中找「类似需求」，含金量不低）

### 业务开发类
- **独立开发小型业务模块**：如用户操作日志、字典管理、报表查询、文件上传。工作内容：设计表结构 → DAO/Service/Controller → 参数校验 → 联调自测。简历口径：「独立完成 XX 功能模块后端接口开发（CRUD、参数校验、联调交付）」
- **接口新增/改造**：增加查询条件、分页、排序、多表关联查询。含金量在「读懂原有业务逻辑、不破坏旧功能」

### 中间件 & 性能优化类
- **给已有查询接口加 Redis 缓存**：不要只做 set/get，要包含缓存 key 设计、过期时间与刷新策略；不做整体缓存架构
- **SQL 优化**：定位慢查询、加索引、改写多表 SQL、避免全表扫描；用 explain 讲优化前后执行计划变化
- **MQ 生产者/消费者**：在现有异步场景发消息/消费消息（如告警后通知、日志异步落库）；不设计 MQ 整体架构

### 工具/自动化/监控/Agent 类
- **Java Agent/探针**：写简单 Agent 采集方法耗时、打印调用日志、性能统计 demo 对接项目
- **定时任务**：Spring Task / XXL-Job 定时统计、同步第三方数据
- **通用工具类封装**：统一返回体、脱敏工具、导出 Excel 工具

### 其他
- **补单元测试**：覆盖关键分支（写代码）

## L2 进阶需求（6 个月以上或冲刺高难度面试才选）

布隆过滤器/去重组件改造、数据权限实现、网关限流、消息重试/死信、线程池统一治理、监控大盘接入。

## L3 高级需求（不输出为机会，仅理解）

整体缓存架构设计、分布式事务方案、MQ 整体架构、网关重构、核心支付/资金链路改造。

## 性价比打分口径（统一尺度，保证不同轮次结果可复现）

对每个机会按以下 1–5 分打分，排序一律用表格展示。

| 维度 | 1 分 | 2 分 | 3 分 | 4 分 | 5 分 |
| --- | --- | --- | --- | --- | --- |
| 技术含金量 | 无技术含量 | 简单业务改造 | 有技术选型或取舍可讲 | 性能/稳定性/并发改进且有可量化结果 | 涉及当下主流技术（缓存/MQ/分布式/高并发），能延伸多道八股文 |
| 面试延伸性 | 无考点可讲 | 1 个浅层考点 | 1–2 个常见考点 | 2–3 个考点且有深度 | 可串讲一串考点并展示项目实践 |
| 可实现性 | 依赖线上环境或他人配合 | 较依赖环境 | 中等，需一定协调 | 大部分可独立完成、少量依赖 | 实习生本地/现有环境即可独立完成 |

- 工时档位：1 = 1–2 天；2 = 约 1 周；3 = 约 1 个月；4 = 1 个月以上。
- 性价比 =（技术含金量 × 2 + 面试延伸性 × 2 + 可实现性 × 1）÷ 工时档位。技术含金量与面试延伸性加权，避免短工时或纯文档机会虚高。
- 排序表每行展示三个单项分与算式；**按性价比分降序自动排位（不允许人工改序）**；并列时按「技术含金量 → 面试延伸性 → 工时（短者优先）」决定位次。
- 排序展示格式：表格列「机会名、级别、技术栈、技术含金量、面试延伸性、可实现性、工时档、性价比分、算式、推荐位次、匹配度」。

## 输出与交互

- 产出 5–10 个机会，按上述口径**降序排位**。
- 每个机会标注两个口径的匹配度：「与当下主流技术匹配度」（高/中/低）指技术本身是否是当下招聘重点；「与投递方向匹配度」（高/中高/中）指与用户目标岗位的契合度。
- 收尾顺序固定：先请用户挑选 1–2 个进入 Stage 3（用户不确定时给出推荐及理由），再提供「确认 / 追问 / 跳过」收尾；「跳过」= 跳过当前阶段确认直接进入下一阶段。
- 不确定的信息（如业务为什么存在、指标口径、线上环境）先问用户；答不上来就标「待确认」，不要编。
